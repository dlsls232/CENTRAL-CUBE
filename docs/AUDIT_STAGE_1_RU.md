## 3. Фактическая функциональность и ограничения

### Сетевой протокол
- Реализован length-prefixed JSON с ограничением кадра 1 MiB.
- Сервер и клиент задают минимальную версию TLS 1.2.
- Сервер требует клиентский сертификат (`CERT_REQUIRED`); клиент проверяет CA-цепочку сервера и дополнительно pin SHA-256 fingerprint.
- Командный allowlist ограничен `ping`, `system_info`, `shutdown`, `restart`, `sleep`.
- Произвольное выполнение shell-команд не реализовано.
- У сервера есть 15-секундный timeout чтения одного запроса; клиент задаёт socket timeout.

### Сопряжение
- Клиентская функция `pair_with_agent()` существует и передаёт код по mTLS.
- Однако TLS-сертификат клиента уже должен быть выдан доверенным CA до pairing: pairing не является bootstrap-механизмом выдачи клиентского сертификата.
- Код одноразовый, 6 цифр, хэшируется с солью, TTL 30–900 секунд, лимит 5 попыток.
- Состояние pairing-кода находится в памяти процесса; при перезапуске агента создаётся новый код.
- Fingerprint после успешного pairing сохраняется в JSON allowlist.

### Anti-replay
- Используется SQLite с `INSERT OR IGNORE`, что обеспечивает атомарное резервирование ID между конкурентными обработчиками.
- Важное ограничение: таблица очищается до последних 100 000 ID. Следовательно, защита не является бессрочной; старый ID теоретически может быть принят повторно после удаления записи.
- Если не задан путь для replay DB, используется только ограниченное in-memory хранилище.
- Это необходимо исправить до production.

### Сертификаты и ключи
- Есть проверка CA и fingerprint, а также allowlist клиентских fingerprint.
- Полноценный CRL/OCSP/revocation workflow, автоматическая ротация сертификатов и управление жизненным циклом ключей не обнаружены.
- UI хранит пути к файлам сертификатов и приватного ключа в SQLite; защита самого приватного ключа средствами DPAPI/Credential Manager не реализована в проверенном коде.
- Обработка TLS handshake и ошибок есть, но полноценное ограничение частоты новых подключений/запросов не обнаружено.

### Команды
- Реальны Ping и System Information.
- Shutdown/Restart/Sleep реализованы через Windows subprocess без shell=True, при включённом администратором флаге и явном `confirmed=True`.
- Выполнение power-команд на Linux намеренно возвращает ошибку.
- Wake-on-LAN реализован как локальная отправка magic packet; удалённая команда WOL через агента отсутствует.
- Полноценный bulk сейчас ограничен TCP check и mTLS Ping; bulk power actions отсутствуют.

### GUI
- PySide6 окно содержит Dashboard, Devices, Bulk Actions, Reports, Guide, Settings, About.
- Обработчики сетевых операций вызывают синхронный клиент напрямую из UI-обработчиков. Это создаёт риск зависания интерфейса на timeout/медленном соединении.
- Bulk Ping выполняется последовательным циклом в UI-потоке.
- Раздел Reports показывает журнал SQLite; экспорт CSV в проверенном коде отсутствует.
- Наличие разделов не доказывает полноту каждого UX-сценария.

### SQLite
- Есть таблицы devices/settings/audit_log, внешние ключи и индексы журнала.
- Есть простая проверка/добавление колонки mac_address.
- Полноценная версионированная система миграций не обнаружена.
- Транзакции стандартного SQLite connection context manager используются; соединение закрывается кастомным классом.

### Windows packaging
- Есть PyInstaller сборка GUI и агента, Inno Setup script и GitHub Actions Windows runner.
- Workflow запускает тесты/coverage/compileall и создаёт executables/installer.
- В доступном workflow нет автоматизированного smoke test запуска обоих EXE, установки/удаления установщика и проверки ярлыков.
- Workflow не был запущен в рамках текущей проверки; никаких Windows бинарников не собрано.
- В Inno Setup `AppVersion` пока 0.1.6, а ярлык рабочего стола опциональный; ярлык меню Пуск предусмотрен.

## 4. Приоритетные риски перед production

1. Бессрочное хранение использованных command_id: убрать ограничение удаления, добавить тесты конкурентной вставки и перезапуска.
2. Реализовать отзыв клиентских сертификатов (CRL/OCSP либо управляемый локальный denylist с проверкой на каждом подключении) и процедуру ротации.
3. Добавить ограничение частоты соединений/ошибочных pairing попыток и верхние пределы ресурсов на клиента.
4. Перенести сетевые операции и bulk задачи из GUI thread в управляемые фоновые задачи; обеспечить отмену и graceful shutdown.
5. Убрать хранение секретного материала в открытом виде; использовать Windows DPAPI/Credential Manager на Windows.
6. Реализовать экспорт CSV, проверяемые миграции SQLite и полный набор тестов для требуемых сценариев.
7. Доработать Windows CI: запуск EXE, smoke tests агента, установку/удаление Inno Setup и проверку ярлыков/иконок.

## 5. Вывод этапа 1

Проект — работающий прототип с реальным mTLS-контуром, SQLite, базовым pairing и 41 проходящим тестом. Но на основании исходного кода его нельзя честно назвать production-ready Windows 1.0.0. Критические пробелы перечислены выше. Следующие этапы должны исправлять их в существующей архитектуре, не переписывая проект с нуля.
